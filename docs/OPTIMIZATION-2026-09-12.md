# YzVibe 当前项目优化与拓展分析

> 后续进展：全部 P1、任务交付卡与连接诊断已在本轮实现，见 [build 11 发布说明](RELEASE-0.1.0-11.md)。下文保留修复前的分析基线。

分析日期：2026-09-12；代码基线：`833522e`。本轮检查代码、历史改动、协议与现有测试，未修改业务实现。

项目已经具备远程编程控制端的主要功能。下一阶段最有价值的方向，是让用户离开电脑后仍能确定：指令有没有送达、任务有没有中断、结果是否值得接受。建议先处理发送与恢复链路，再将已有消息、工具记录和 diff 整理成任务交付体验。

## 当前能力与判断依据

- Node.js 桌面连接器与 SwiftUI iOS App 已形成主链路：配对、多地址连接、会话、队列、审批、图片、文件、diff、通知、用量、终端历史导入。
- Codex 已在当前服务端通过 `codex-app-server.js` 接入，包含手机审批与用户问题回答；旧架构文档中的“Codex 不支持手机审批”已过时。
- 已有四个固定首句模板、会话内存草稿、活动总览、系统已有 Live Activity 恢复、测试与 CI。这些方向应在已有实现上深化。
- Android、小程序仍只有占位目录。
- 连接器现有测试 **74/74 通过**。本轮 iOS 仅做源码与测试覆盖检查，未运行模拟器、真机、真实 Agent 或 APNs 端到端测试。

下文“已复现”指隔离执行当前源码得到结果；“代码确认”指直接可见的实现行为；“产品建议”需要在后续使用反馈中验证收益。工作量为熟悉项目的一名开发者的粗估，包含相关回归验证，不构成排期承诺。

## 一、优先优化

### 1. 消息发送结果与附件完整性：P1，先做

**代码确认。** [ChatView.swift](../ios/Sources/YzVibeKit/Features/Chat/ChatView.swift) 的 `submit`（205 行起）在上传和发送之前清空文字与图片。图片上传失败只会返回 `nil`，循环仍继续，随后可能只发送文字或部分图片。[AppStore.swift](../ios/Sources/YzVibeKit/Store/AppStore.swift) 的 `send`（490 行起）用同一个 `false` 表示“发送成功但未排队”和“发送失败”；失败时仅显示 toast，本地气泡没有失败/待确认状态。

服务端 [server.js](../connector/src/server.js) 的消息入口（373 行起）没有客户端消息 ID；`handleSend` 每次都会新增消息或队列项。因此响应丢失后，用户再次发送可能导致重复执行。当前客户端已经避免自动重放写请求，这一点应保留。

建议分两步：

1. 返回明确的发送结果；失败保留草稿和图片，标记失败或结果待确认；任一附件上传失败时保留整条待发送内容。恢复草稿时避免覆盖用户在请求期间新输入的文字。
2. 引入持久化 `clientMessageId` 与发送箱；连接器在派发前持久化接收记录，重试返回同一接收结果。区分“连接器已接收”“Agent 已接收”“执行结束”；Agent 接收结果不确定时先对账，不能仅靠去重表宣称执行恰好一次。

验收：请求未发出、响应丢失、重复点击、App 重启、连接器重启、第二张图片上传失败都可追踪；同一个客户端消息 ID 不产生第二条队列项，也不在结果不确定时静默再次派发。

工作量：先修交互 **1–2 天**；完整发送箱与接收去重 **3–5 天**，Agent 不确定派发的对账需单独验证。

### 2. 前台重连后的事件补齐：P1，先做

**代码确认，用户表现待网络故障测试。** [ConnectorClient.swift](../ios/Sources/YzVibeKit/Networking/ConnectorClient.swift) 的 `SocketBox.receive`（545 行起）断线后自动重建连接，但事件模型只有 `disconnected`，没有重连成功后的同步通知。AppStore 收到断线只将设备标为离线；`resync` 主要由启动、回到前台或推送等入口触发。

因此，App 始终停留在前台、网络断开期间出现回复或审批、随后 WS 自动恢复时，旧事件没有补齐触发。收到新的流式片段也无法还原缺失的中间文字。

短期增加确认连接成功后的同步入口，合并重复同步请求。同步时需处理“快照请求过程中到达新事件”的顺序，避免旧快照覆盖新状态。后续增加事件序号、快照版本和恢复游标，支持去重、补齐和过期游标回退。

验收：App 不退后台，断网期间产生回复、工具完成、审批请求与审批解决；恢复连接后与服务端状态一致，文字不缺段、不重复，已解决审批不会重新变成待审批。

工作量：重连补数与故障测试 **2–3 天**；版本化增量恢复 **4–7 天**。

### 3. 流式消息持久化与异常状态恢复：P1，已复现

[store.js](../connector/src/store.js) 的 `appendDelta`（301 行起）只追加内存和广播；消息结束、工具更新等操作才保存完整文件。启动时会话状态被重置为 `idle`，磁盘消息里的 `streaming` 标记却没有相应恢复处理。

隔离复现：创建会话 → 设置 running → `appendDelta("already delivered text")` → 用新 Store 读取相同目录。结果：内存里已有正文，重载后正文为空、`streaming=true`、会话为 `idle`。

这说明 YzVibe 状态库可丢失最近一次保存之后的流式内容；本实验不说明 Claude/Codex 自身的 transcript 也丢失。已接管会话在当前 `resolveSession` 中优先读取 Store，不能默认依赖终端历史自动修复。

建议将消息增量写入可恢复的追加记录，或先做有明确丢失窗口的定时检查点；启动时为未结束轮次标记“执行结果待确认”，并对齐消息与工具状态。进一步考虑用事务存储承载消息、发送箱与事件版本，保留旧 JSON 数据迁移和回滚路径。

验收：在回复中途终止连接器后重启，已保存内容可恢复；未结束状态有明确解释；不会仅因重启而把未确认任务显示为正常完成。

工作量：检查点与恢复状态 **2–3 天**；统一事务存储另计。

### 4. 请求体限制与参数校验：P1，对外使用前补齐

**代码确认。** [server.js](../connector/src/server.js) 的 `readBody`（210 行）一直收集 chunks 后再 `Buffer.concat`。公开 `/pair` 在检查配对码前也走此逻辑；上传接口的 20 MB 限制在完整缓冲后才检查。大小限制因此不能限制接收阶段的内存占用。

建议在读取过程中计数，超过路由限制即拒绝并释放资源；给 JSON、图片、WS 消息设置各自上限，校验 text、attachments、mode 等字段类型和数量。异常输入返回明确的 400/413；用受控夹具验证，不对真实隧道做压力测试。

工作量：**1–2 天**。

### 5. 长会话同步与写盘成本：P2，有规模证据

当前每次工具卡更新都同步重写整份会话消息 JSON；恢复时按设备、按已打开会话串行拉完整历史。[AppStore.swift](../ios/Sources/YzVibeKit/Store/AppStore.swift) 的 `resync` / `catchUpMessages`（183 / 239 行）和 [store.js](../connector/src/store.js) 的 `upsertToolCall`（324 行）是优先入口。

本机合成基准：每条正文为 2,000 个 ASCII 字符，1 次预热、15 次工具更新采样。

| 消息数 | 消息文件大小 | 单次同步更新中位耗时 | 采样最大耗时 |
| --- | ---: | ---: | ---: |
| 100 | 0.22 MB | 0.44 ms | 0.81 ms |
| 1,000 | 2.24 MB | 3.27 ms | 4.09 ms |
| 5,000 | 11.18 MB | 16.43 ms | 18.72 ms |

这是 Node 单进程的同步存储成本，不是手机帧率或生产网络延迟。它说明一次很小的工具更新会随完整历史增长而变贵，并占用处理 HTTP/WS 的同一事件循环。

建议按优先顺序做：消息分页、先恢复当前打开会话、不同设备有限并发同步、按版本获取变化；将消息写入从整文件重写改为增量持久化。保留全量快照作为恢复兜底。性能验收同时观察历史完整性、响应时间、事件循环延迟与传输量。

工作量：分页与同步调度 **3–5 天**；统一存储改造及迁移 **1–2 周**。和第 3 项共同设计，避免先后做两次持久化改造。

### 6. 多设备通知与关键控制反馈：P2

**代码确认。** [server.js](../connector/src/server.js) 的 `phoneOnline`（106 行）判断任意 WS 在线，就在回复完成时跳过全部手机的推送（141 行）。一台设备在线时，另一台已配对但离线的设备可能收不到完成通知。应按 deviceId 判断在线状态和通知偏好；当前测试未覆盖两台设备的这一组合。

另外，iOS 审批已经走带 HTTP 响应的请求，停止任务仍走 WS send（[ConnectorClient.swift](../ios/Sources/YzVibeKit/Networking/ConnectorClient.swift)，226 行）。可复用已有 POST stop 接口，显示“正在停止”，直到收到实际任务终态或超时提示。服务器收到停止命令与 Agent 真正停止是两个不同阶段。

验收：两台手机一台在线、一台离线，分别收到正确反馈；点击停止后有可追踪结果，未知结果不会显示已停止。

工作量：**1–2 天**，真实通知场景还需真机验证。

## 二、最值得拓展的产品能力

| 顺序 | 方向 | 最小可用版本 | 用户价值与前置条件 |
| --- | --- | --- | --- |
| 1 | 任务交付卡 | 每轮结束显示结果、修改文件、执行检查、失败项、产物入口；每项能追溯原始记录 | 手机快速验收工作。先补齐轮次记录和工具结果链路；不能把模型口述或普通命令 exit 0 等同于测试全部通过 |
| 2 | 连接诊断页 | 展示当前地址、候选地址探测、身份匹配、Agent 可用状态、最后同步错误、推送状态；导出脱敏诊断包 | 降低“为什么连不上/不回复”的排障成本，复用现有 CLI status、/health 和推送自检 |
| 3 | 项目工作区与可编辑任务模板 | 保存设备、目录、常用 Agent/模式/模型、任务模板参数；从项目一键启动任务 | 现有四个模板是固定文案，收藏目录和会话选项较分散；项目预设能减少手机重复输入 |
| 4 | 任务级 worktree | 新任务可选隔离分支和目录；结束后查看差异、保留或清理，明确发起合并 | 多会话并行更容易管理；需设计未提交改动、依赖准备、冲突和退出清理，工作量较大 |

交付卡建议先记录结构化轮次：`runId`、开始/结束时间、终态、检查命令与结果来源、关联文件和产物。当前模型主要是 Session / Message / ToolCall，缺少稳定的轮次交付对象。第一版可直接组织已有数据；对未知或截断的结果明确显示“未验证/信息不完整”。估计 **3–5 天**可做有限范围版本。

工具结果的产品取舍需要延续近期设计：提交 `8af1568` 主动将聊天工具详情改为仅展示命令。[ToolCallCard](../ios/Sources/YzVibeKit/Features/Chat/ToolOutputView.swift) 当前不渲染输出。同时 WS 解码（ConnectorClient 610 行）与已有工具卡合并（AppStore 690 行）均忽略 output/outputKind/truncated，与 REST 快照包含的数据不一致。可在交付卡或二级详情提供结果核验入口，保持当前聊天页的简洁；即使维持不展示，也应使数据模型和协议行为一致。

诊断页可以先落地，估计 **2–3 天**。当前客户端将多数失败压成“HTTP 状态码”或离线状态，连接器 `/health` 返回静态 Agent 名称，不能直接代表已安装或已登录。为错误增加可识别代码与可恢复建议，诊断包默认排除 Token、密钥和会话正文。

项目预设估计 **2–4 天**。任务级 worktree 估计 **1–2 周以上**；已有 `baseCommit` diff 表示“基线以来的仓库差异”，仍可能包含会话开始前的未提交修改，不能直接拿来宣称全部改动属于当前任务。

Android / 小程序建议作为之后的客户端扩展。先稳定发送确认、事件恢复、错误语义和协议契约，再复用这套能力，可以减少同类问题在多端重复修复。

## 三、工程维护与文档

1. **建立跨端协议夹具。** 连接器产生真实 JSON 事件，iOS 测试实际解析和合并结果。现有工具输出测试主要验证模型解码和完整快照恢复，不能覆盖 WS 输出字段遗漏；新增覆盖应围绕丢失响应、重连间隙、附件失败等真实场景。
2. **让协议可演进。** 将版本、功能能力、结构化错误、客户端消息 ID 和事件游标纳入同一份契约；为未知字段、缺省字段及不支持能力定义行为。
3. **按职责逐步拆分。** AppStore 823 行、ConnectorClient 707 行、Models 966 行、server.js 647 行。优先在上述工作中提取发送状态、连接恢复、任务记录和请求校验，降低不同功能共同修改同一文件的概率。
4. **更新当前能力说明。** [README](../README.md) 仍称 Codex Normal 不发手机审批；[ARCHITECTURE](ARCHITECTURE.md) 仍指向 exec 驱动；[protocol](../shared/protocol.md) 配对时效同时写 5 分钟和 10 分钟，Codex 用量说明也含旧实现。当前能力应以生产导入的 app-server 驱动为准，并注明旧 exec 驱动的保留用途。
5. **对齐输出承诺。** README 宣称能看命令真实输出，当前工具详情页只展示命令；应随交付卡方案同步调整产品说明。

这些文档改进可作为半天到一天的独立整理；本轮保留原文，避免将尚未实施的建议写成已实现功能。

## 四、建议实施顺序与验证范围

1. **第一轮：可靠发送与恢复。** 草稿/附件失败处理、明确发送状态、前台重连补数、流式恢复状态、请求体限制；同时设计发送箱与持久化接收记录。验收以故障注入下“没有静默丢失或重复派发”为准。
2. **第二轮：交付与排障。** 有证据来源的任务交付卡、连接诊断、跨端协议夹具、文档对齐；同时补多设备通知和停止反馈。
3. **第三轮：规模与并行任务。** 根据真实长会话测量推进分页/增量存储，再做项目预设、worktree 和其他客户端。

本轮实际执行：连接器 `npm test` 74 项通过；Store 重载实验；三档合成会话的同步写盘基准。首次测试因沙箱限制本地监听端口/临时目录而失败，授权重跑后通过。所有实验使用临时数据，未操作用户实际会话或连接器状态。

仍需后续验证：iOS 前台断网恢复、图片上传失败交互、真实 Agent 派发对账、两台真机通知、APNs/Live Activity 生命周期，以及实际项目规模下的性能。上述估算与排序可据这些结果调整。
